# Phase 3 方向决策备忘(草稿)

状态:待定 | 写于 r22 | 决策输入:求职背书价值 × 生态空白 × 工程成本

## 候选 A:VLM 自动标注 / 数据引擎层

**做什么**:接入开源 VLM(Qwen2.5-VL / SmolVLM)对 episode 关键帧打语言标签,
生成 task 描述 / 段落分割 / 质量分补充;产物直接写入 LeRobot tasks 体系。

- 面试叙事:数据引擎(data engine)是具身智能招聘最热的方向之一
  (Physical Intelligence、1X、智元都在讲 data curation)
- 与平台契合:QC 评分已经产出"哪些帧值得看"的信号,VLM 是其自然上层
- 生态空白:LeRobot 生态没有统一的 episode captioning 工具(各实验室自写脚本)
- 成本:需要 GPU 推理;无卡机器只能 mock — 但平台本身是 CPU 工具链,加 VLM
  会破坏"轻依赖"卖点 → 必须放 extras 且默认关闭
- 风险:模型质量决定可用性;面试演示需要真实跑通的例子

## 候选 B:机队编排(fleet)/ 采集工作台

**做什么**:多机采集任务分派 + 采集进度目录同步 + 版本化快照(数据集"提交"概念)。

- 面试叙事:基础设施/平台工程岗位的强背书(分布式、一致性、运维)
- 与平台契合:catalog+API 已是中心化底座,机队是它的横向扩展
- 生态空白:自托管机队采集管理在开源侧确实没有成熟品(对比 Foxglove 组织版)
- 成本:纯 CPU,零新依赖,延续卖点;但演示需要多机环境(可模拟)
- 风险:没有真机队时故事略空;价值主张偏企业向

## 初步倾向(待用户输入)

A+B 混合顺序:**先做 B 的版本化快照**(dataset "commit/rollback" — 小、自包含、
演示不需要 GPU),它同时是 A 的前置(标注产物需要可版本化地挂回数据集)。
A 的 VLM captioning 作为 v0.3 目标,期间用 OpenRAL/LeRobot 的贡献轮换等待。

## 决策需要的外部输入

1. 目标岗位 JD 里"数据平台"vs"数据引擎"哪个更近?
2. 有无 GPU 可用(决定 A 的演示深度)?
